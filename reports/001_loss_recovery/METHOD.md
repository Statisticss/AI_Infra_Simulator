# 实验 001：故障丢包下的 RDMA 恢复机制

本实验回答两个问题：传统按序接收 + Go-Back-N 与乱序接收 + 选择性重传有多大差别；
5% 故障丢包下，90% Goodput 在哪些条件下可能成立。
它是 Python 3.10 的分组级机制仿真，不是商用网卡测评，也不是完整的 UET 一致性实现。

## 原文与协议依据

找到了与问题描述一致的 [CIPU 文章](https://zartbot.github.io/blog/arch/cipu/index.html)，
第 2.4 节将 5% 丢包、90% Goodput 的结果归于 CIPU 2.0，并讨论多路径和 SACK。
文章没有给出足以复现实验的 RTT、MTU、并发连接数、消息大小、丢包注入位置、
反馈包是否丢失以及 Goodput 分母。因此本实验检验机制与数字的可行性，不声称复现 CIPU。
文中也没有提供 CIPU 2.0 与 UET 标准等同的证据。

使用 [UE Specification 1.0.3](https://ultraethernet.org/wp-content/uploads/sites/20/2026/08/UE-Specification-1.0.3.pdf)
作为参考（2026-07-16 发布，2026-10-07 查阅）。本次选择 RUD 方向，参考：

- §3.5.11–3.5.12：累积 ACK、独立 ACK PSN、64 位 SACK bitmap 和 ACK 合并。
- §3.5.15：Trim/NACK、RTO 及实现可自行选择的早期丢包检测。
- §4.1：Trim 适用于通过校验但未通过缓冲准入的包；故障导致的完整包丢失不能凭空变成 Trim。

**UEC 是联盟，UET 是传输协议；UET 还有 ROD 等模式，并非所有模式都等于本实验的 RUD。**
本模型不实现连接建立、SES 全语义、CLEAR 握手、安全、拥塞控制或协议报文编码。

传统机制参考 [IRN / Revisiting Network Support for RDMA，SIGCOMM 2018](https://cs.nyu.edu/~apanda/assets/papers/sigcomm18-irn.pdf)
§2–3，以及 [Alibaba HPCC 的 ns-3 模型](https://github.com/alibaba-edu/High-Precision-Congestion-Control)
中 `ReceiverCheckSeq` 和 `RecoverQueue` 的顺序检查与发送游标回退行为。
并未把旧论文或该平台的默认链路参数当作当代网卡实测参数。

## 模型与公平性

| 项目 | 传统 RoCE RC / GBN 模型 | UET RUD 机制模型 |
|---|---|---|
| 路由 | 单条等时延有序路径 | 四路径逐包轮转，路径有固定时延差 |
| 接收 | 丢弃超前包，只接受下一个 PSN | 接收并保留乱序包，精确去重 |
| 反馈 | 累积 ACK、序列差错 NACK | 累积 ACK、ACK PSN、64 位 SACK、Trim NACK |
| 重传 | 从首个未确认 PSN 回退 | 只重传未被正向确认的 PSN |
| 隐式故障检测 | 后续失序触发 NACK，尾包依赖 RTO | 后续 ACK 的正向证据 + 时间保护，尾包依赖 RTO |

两个模型使用相同带宽、有效载荷、固定报文开销、窗口配置和主实验丢包分布。
喷洒不会扩大端口总带宽；这里的网络不超售、没有交叉流和路径拥塞，
所以不测量喷洒的负载均衡收益。主要差别是故障恢复与乱序处理。
传统模型不代表所有现代 RoCE 网卡：厂商可能加入选择性重传等扩展。

使用与 [ns-3 离散事件方法](https://www.nsnam.org/docs/manual/html/events.html) 相同的基本思路，
在 Python 中维护有时间戳的事件堆，而不是逐纳秒步进。
固定有序路径的 GBN 接收事件可以合并计算，其反馈仍在正确的未来时间返回。
测试将此加速与逐包显式接收事件逐项比较；丢包及重传次数没有抽样缩小。

## 主实验参数

| 参数 | 设定 |
|---|---|
| Python | 3.10.19 |
| 端口速率 | 400 Gbit/s，MAC 侧字节预算，不另计 PHY/FEC 编码开销 |
| 数据有效载荷 | 4096 B；最后一个包允许不足一整包 |
| 数据线速开销 | 每包统一 128 B，包含本模型中的所有固定封装与间隔预算 |
| 反馈包 | 96 B，正常接收每 4 包反馈；尾包、重复包、重传包会触发反馈 |
| 数据故障 | 每次发送独立 5% 丢失，重传包同样可能丢失 |
| 反馈故障 | ACK/NACK 独立 5% 丢失 |
| Trim | 主实验为 0；单列合成 Trim 对照 |
| RTT | 10 / 100 / 1000 us；是往返传播及固定处理时间，不含逐包序列化 |
| 路径时延差 | UET 四条路径的单程时延总跨度 2 us，平均与 GBN 相同 |
| PSN 范围窗口 | 8 倍基础 BDP，向上取整，最大 32640 包；两种机制相同 |
| 早期恢复 | 发送后至少 1.5 RTT；还必须见到更高 PSN 的正向 ACK 证据 |
| 重排保护 | 早期阈值同时不得小于 RTT + 单程时延跨度 + ACK 合并等待 |
| RTO | 基础 4 RTT；UET 对连续超时采用指数退避，上限 8 倍基础值 |
| AllReduce | 8 个 rank，32 / 256 / 1024 MiB 每 rank；每邻居一条逻辑传输连接 |
| 重复 | 每个有损条件 5 个独立种子：11、29、47、71、101 |

128 B 和 96 B 是**受控实验中的统一预算，不声称是协议的精确固定头长**。
ACK 合并方式有小差别：UET 有 0.5 us 延迟 ACK；GBN 在发送窗口边界请求 ACK，防止小窗口死锁。
无损路径没有随机时延，因此每个无损基线只需运行一次；相同的无损流可精确复用。

## 故障、Trim 和 SACK 的边界

5% 表示传输层看到的**残余分组丢失概率**，不是原始比特误码率。
主实验不运行 PFC、FEC 或链路层重试，也不制造拥塞丢包。
随机独立丢包是压力测试模型，不能替代真实光链路故障测量。

Trim 对照将 5% 的有效数据包变成仅通知丢失的头部，到接收端后才产生 NACK。
它只是**丢失通知机制的对照**，不模拟真实交换机队列准入，也不预测拥塞控制效果。
发送端仍支付原数据包的发送序列化成本。故障包不会生成这种通知。

SACK 的 0 位表示“没有新增信息”，不能撤销之前收到的 1 位。
源端只能读取真实返回的反馈及自身计时器；不会访问随机丢包器的结果。
早期重传策略是本实验的实现选择，不是 UET 规范规定的唯一算法。
ACK PSN 的重复确认可能有益，丢失的反馈仍可能带来多余重传，均计入结果。

突发对照使用全好/全坏两态马尔可夫过程，稳态丢包比例为 5%，
坏状态平均持续 8 次数据包发送。该“8”以包数衡量，**不是持续时间型链路中断**。
链路闪断、特定路径黑洞与故障后路由收敛需要后续专门模型。

## AllReduce 调度与 Goodput

主模型为保守的分步 Ring AllReduce：ReduceScatter 和 AllGather 各 `N-1` 步；
每一步所有 rank 并发发送 `S/N` 字节，并等待该步最慢的发送完成确认。
因此：

```text
T_allreduce = sum_over_2(N-1)_steps(max_over_N_ranks(T_transfer))
algbw = S / T_allreduce
busbw = algbw * 2(N-1)/N
reported_goodput = busbw / link_rate
```

这使用 [NVIDIA nccl-tests 的 bus bandwidth 换算口径](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)。
8 rank 的换算系数为 1.75。报告不把不同 rank 的发送字节相加后除以单端口带宽，
也不把 `S/T` 直接称为链路利用率。重复包只消耗资源，不增加有效字节。

同时记录同一协议、同一参数的无损基线，`retained_vs_zero_pct` 表示相对无损时的保留比例。
绝对线速百分比、无损性能保留比例和算法带宽是三个不同指标。
发送完成时间包括最后一个 ACK 的返回；接收完成时间另外留在逐流记录中。

这是通信行为模型，不执行 GPU 张量运算；它按完整 Ring 的数据量和依赖调度通信。
各逻辑链路具有独立的数据/反馈序列化器，不实现实际 NIC 上来自多个邻居的数据与 ACK 的竞争。
报告记录反馈/正向线速字节比，帮助评估该简化的量级。
本模型也没有 NCCL 的多 channel、子块流水化、GPU 归约开销、PCIe 限制、
不对称站点布局或共享跨站点瓶颈，结果不能视为生产 NCCL 的预测。

## 可检验的边界

对独立残余数据丢失概率 `p`、有效载荷 `L` 和固定开销 `H`，
忽略启动、尾部恢复和空闲的长流上界为：

```text
G / C <= (1-p) * L/(L+H)
```

本实验 5% 丢包、4096 B 有效载荷、128 B 开销对应 92.12% 渐近上界；
无开销时为 95%。90% 接近上界，要求窗口、恢复时延、消息大小及反馈效率都合适。
1 KiB 有效载荷和同一开销对应 84.44% 上界，即使理想选择性重传也无法达到 90% 线速。
有限随机样本的实测丢包比例不严格等于设定概率，上式是期望/渐近界。

主窗口按**整个未累积确认的 PSN 跨度**限制新数据，
不会通过只统计未确认包数量来掩盖接收重排空间需求。
大 RTT 时 BDP 增大，固定 512 包窗口与适配 BDP 的窗口应当分开比较。
