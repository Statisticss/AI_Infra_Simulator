# 实验 002 / 003 方法：反馈覆盖、尾部恢复与长距离窗口

本研究延续 [实验 001](../001_loss_recovery/METHOD.md)，保留其原始模型和结果。
新增 `advanced_transport.py` 通过共享事件时钟和端口仲裁器承载多个独立 PSN 空间。
它是机制研究，不是 CIPU 仿真器、完整 UET 实现或真实网卡测试。

## 固定条件与口径

| 条件 | 取值 |
|---|---|
| Python | 3.10.19；运行器拒绝其他主/次版本 |
| 速率 | 单个 400 Gbit/s 全双工端口，MAC 侧字节预算 |
| 包长 | 4096 B 有效载荷 + 128 B 统一固定开销；不声称是精确 UET 头长 |
| ACK | 96 B，每 4 包或 0.5 us 触发；重传/尾包等会立即确认 |
| 损失 | 每次原始包、重传包、冗余副本均独立经历配置损失率 |
| 反馈损失 | 与数据相同的损失率、独立随机过程；不设置无损 ACK 特权 |
| 路径 | 四条固定时延路径，单程总跨度 2 us，平均 RTT 不变；另测 100 us 跨度 |
| Trim | 0；研究物理故障残余丢包，不制造交换机拥塞 |
| 003 RTT | 1、2、5、10 ms，不含逐包序列化 |
| 003 主矩阵 | 每次 1 GiB 完整传输；丢包 0、0.1%、1%、3%、5%、10% |
| 资源约束 | 不超过 2 GiB 聚合 PSN 窗口有效载荷预算，最多 64 个 PDC |
| 统计 | 主评估有损点 5 个种子；长流/跨域 AllReduce 为 3 个；无损确定性点 1 次 |

零丢包点的路径和时序是确定性的，所以只运行一次；没有用一次有损流外推多次运行。
延迟、重复包、空闲等待以及最后一次确认都计入完成时间。
Goodput 主指标为 `有效字节 × 8 / 完成时间 / 400 Gbit/s`。
图表中的 95% CI 是独立运行均值的 Student-t 区间，仅描述抽样误差，不包括建模误差。

纯重传的渐近参考为 `(1-p) × payload/(payload+overhead)`。
另给有限消息的理想流体参考：

```text
T_reference = total_original_wire_bytes / ((1-p) × C) + RTT
G_reference = payload_bytes / T_reference / C
```

这个参考忽略窗口阻塞、恢复轮次和最后若干丢包，按期望损失计费；
它是帮助解释有限消息的乐观参考，**不是每一次随机样本都必须满足的严格上界**。
不能将 1 GiB 的完成 Goodput 与无限长流的渐近吞吐混为一谈。

## 比较哪些策略

| 标识 | 恢复策略 | 窗口 |
|---|---|---|
| `uet` | 实验 001 的 UET RUD 风格基线：轮转 SACK、1.5 RTT 早期恢复、4 RTT RTO | 单 PDC，8 BDP，上限 32640 包 |
| `cipu_candidate` | 重叠 SACK + 区间收尾反馈 + 更短计时器 + 尾部冗余重传 | 与基线相同 |
| `coverage_fixed` | 与优化方案相同的恢复机制 | 与基线相同，单 PDC |
| `window_only` | 基线恢复机制 | 与优化方案相同的多个 PDC 和聚合窗口 |
| `optimized` | 候选恢复机制 + 预先搜索选定的尾部副本数 | 按 BDP 配置多个 PDC，受内存和连接数限制 |

`coverage_fixed` 和 `window_only` 分开测量恢复算法与窗口资源的收益。
基线只是一个公开可运行的实现选择；差的基线结果不能解释成“所有 UET 实现都这么慢”。

## 正向 SACK 覆盖与尾部策略

每条连接保留 CACK、ACK_PSN 和 64 位 bitmap。bitmap 的零位不撤销已有确认；
发送端只读取真正返回的控制包和自身时钟，从不读取损失发生器或接收端内存。

普通候选 ACK 从 `floor(max(0, trigger_PSN-56)/8)*8` 开始覆盖 64 个 PSN，
相邻反馈具有重叠，降低控制包丢失造成的信息空洞。
跨过一个 64 包区间后，在一个、两个重排保护时间之后各发送一次区间状态。
保护时间是 `路径总跨度 + ACK等待`。已经被 CACK 覆盖的旧区间不再使用超范围负偏移。
ACK/NACK 在共享的反向串行器上排队，每份都付出 96 B 成本，且可能丢失。

选择性早期恢复要求见到更高 PSN 的正向 ACK 证据，且距离最近一次发送至少经过：

```text
max(1.1 × RTT, RTT + path_spread + ack_delay)
```

候选基础 RTO 为 1.25 RTT，持续超时指数退避（最多基础值 8 倍）；尾包无需后续 ACK 也能恢复。
只有全部原始包已经发送、且本 PDC 未确认数不超过 32640 时，重传才使用搜索选定的尾部副本数。
因此一个 PDC 的最后一批仍可能很大，并非只复制消息最后一个包。报告计入其字节和代价。
每个副本单独排队、发送、丢失；ACK 抵达时取消队列中尚未发送的副本。

这借鉴 [RFC 8985](https://www.rfc-editor.org/rfc/rfc8985.html) 的时间保护及尾部恢复思想，
不声称实现了 RFC 的完整 RACK-TLP、拥塞控制或动态重排估计。
固定且预先标定的 RTT 是本实验前提；无法在未知队列时延下直接照搬 1.25 RTT。

## 多 PDC 不是增加链路带宽

所有 PDC 共享一个数据串行器和一个反向反馈串行器。
数据端口按包对当前可发送的 PDC 轮转；空闲 PDC 不阻塞其他连接。
新数据必须满足该连接的 `next_PSN < CACK + window`；优先发送本连接的待重传包。
每个 PDC 的窗口不超过 32640，分配值之和严格等于聚合预算。
绝不将 K 条各自 400 Gbit/s 的独立流相加成一条“400 Gbit/s 优化流”。

400 Gbit/s 下的线速 BDP 为 1 ms 时 50 MB、10 ms 时 500 MB。
单 PDC 的 32640 包对应 127.5 MiB 有效载荷窗口；10 ms 时甚至不足一个 BDP。
窗口必须容纳传播中的数据、尚未返回的确认，以及缺口修复期间的 PSN 范围。
只有正向 SACK 而 CACK 缺口不前进时，PSN 范围仍会阻塞新数据。

2 GiB 是聚合窗口中**有效载荷对应的状态/在途预算**，不是已证明可放入 NIC SRAM 的容量。
实际实现可涉及主机/GPU 缓冲区、描述符、bitmap 和重放元数据；这些各自的成本本次未模拟。
报告同时给出配置窗口容量及实际观察到的乱序有效载荷峰值，两者不能混用。
为跨多个 PDC 条带化一个逻辑消息，应用/传输层还需正确实现最终完成和跨连接顺序语义。
本模型只在全部条带确认之后报告逻辑消息完成，不实现完整 RC Verbs/SES 语义。

## “最优”的明确范围与独立验证

在写定的固定参数和资源限制下，搜索 9 组候选：
目标聚合窗口 `{2,4,8} BDP` × 尾部重传总副本数 `{1,2,3}`。
区间反馈份数为 2，计时器固定，未搜索拥塞控制、编码、包长或拓扑。
训练场景为 1 GiB、5% 独立丢包、RTT `{1,10} ms`，随机种子 `{3,7}`，共 36 个任务。
选择这些完整完成 Goodput 的几何平均最高者；距最好值 1% 内，优先较少窗口资源，再优先较少副本。

选定参数写入 `selection.json` 后，主矩阵才使用独立的 `{11,29,47,71,101}` 运行。
无测试结果参与选参；报告包含所有候选得分，不只展示赢家。
这叫**给定候选集合和训练目标下的最优**，不证明协议空间中的全局最优，也不保证每个损失点都最优。
源码或搜索配置改变后，运行器拒绝沿用旧选择结果和不匹配的检查点。

## AllReduce 的范围

8 rank 的通信专用、分步 Ring：每步每个 rank 发送 `S/8`，各步等待最慢 rank 完成，
ReduceScatter 与 AllGather 合计 14 步。Goodput 为：

```text
T = sum(max(T_rank) for each of 14 steps)
algbw = S / T
busbw = algbw × 2 × (8-1)/8
Goodput = busbw / C
```

换算依据为 [NVIDIA nccl-tests PERFORMANCE.md](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)。
它不是 NCCL 实际的流水内核或站点拓扑仿真。003 将所有逻辑邻居 RTT 均设为长 RTT，
用于检验全球同步与收尾惩罚；不能直接代表“两个机房、机房内短 RTT”的真实系统。
延续 001 的独立逻辑链路假设，**没有把邻居的数据与本 rank 的反向 ACK 合并到同一个物理 NIC 发送队列**。
因此 Ring 结果略偏乐观；本次严格共用端口约束适用于每次消息的所有 PDC。
反馈字节占比单列，不能据此把模型数字当成网卡验收性能。

## 验证、可复现性和未覆盖项

测试包含：旧引擎逐项等价、无损解析序列化时间、多个 PDC 不放大端口带宽、非整包字节守恒、
真实尾部/反馈丢失、重传副本再次丢失、反馈不能早于 RTT、乱序不误重传、窗口与 SACK 偏移、
最慢 rank、AllReduce 字节换算，以及训练/评估种子分离。
每个仿真任务还执行字节预算、重传计数、乱序状态预算和完成性断言；不报告未完成传输的 Goodput。

保存配置、随机种子、源码 SHA-256、Python/平台、Git 起始版本及脏状态、所有逐流结果和耗时。
原始逐流 JSON 放在仓库同级 `results/`；CSV、搜索结果和小图随代码上传。
配置/CSV 中的 `ranks` 是 Ring 的配置参数；`bulk` 忽略该参数，每个任务只传输一条逻辑消息，
可能按 `pdcs` 分成多条共享端口的传输连接。种子按 rank/step 派生后，额外 PDC 使用单独的哈希命名空间，
测试确保各 rank 与 PDC 不重用随机流。

未包含交换机拥塞/排队、PFC、DCQCN/UET-CC、CIPU 自研拥塞控制、链路级 FEC/重试、
毫秒级黑洞及路由收敛、GPU 归约计算、计算通信重叠、在线 RTT 估计和动态负载均衡。
突发损失对照沿用平均连续丢 8 个发送尝试的两态模型；它不是持续时间型光纤闪断。
该两态过程按 PDC 独立生成。因此多个 PDC 时，“8”也是每个 PDC 的发送尝试数，
条带数改变会改变物理端口上的聚合损失相关性。WAN 突发对照仅是每连接故障过程的压力测试，
**不能据此声称对同一个物理链路突发轨迹的公平性能优势**；实验 002 的突发对照双方均为单 PDC。

## 协议依据

参考 [UE Specification 1.0.3](https://ultraethernet.org/wp-content/uploads/sites/20/2026/08/UE-Specification-1.0.3.pdf)
§3.5.11–12 的确认信息、§3.5.15 的恢复机制及 §4.1 的 Trim 边界。
标准允许不同早期恢复实现；本模型选取 RUD 风格，不能代表所有 UET 模式。
32640 是本实验使用的常规最大 MPR 编码；标准另有零编码 override/忽略范围的配置，
所以它**不是所有可能 UET 实现不可突破的绝对窗口极限**。
本研究通过多个有界 PDC 比较资源扩展，避免默默忽略该字段及 SACK 偏移限制。
