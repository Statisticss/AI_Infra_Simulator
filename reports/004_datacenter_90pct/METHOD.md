# 实验 004：场景、协议与计量方法

本实验回答一个存在性问题：能否在现代 AI 数据中心的合理配置中，让 5% 故障丢包下的完整通信 Goodput 超过端口速率的 90%。
场景在 seed 3 的试跑后固定，再运行未参与试跑的 10 个种子。没有根据正式种子筛掉低结果。
它不寻找全局最优协议，也不声称复原 CIPU 2.0 或完整实现 UET。

## 场景为什么合理

- 8 个 GPU rank 分布在 8 个端点，每个端点独占一个 400 Gbit/s 全双工端口。
  [NVIDIA ConnectX-7 手册](https://networking-docs.nvidia.com/connectx7hw/introduction)列出了单端口 400 GbE 与 PCIe 5.0 x16 配置；这里仅借此确定硬件速率量级，不模拟这款网卡的固件。
- 每包 4096 B 有效载荷、128 B 总线速预算开销、每个 ACK 96 B。
  [UEC 官方说明](https://ultraethernet.org/accelerating-ai-with-open-standards-uecs-expanding-vision/)把 4096 B 作为许多工作负载的目标包长，并讨论基本 UET 包的 104 B 头部。
  本实验的 128 B 是统一预算假设，含协议头、帧开销及帧间开销的额度，不是逐字段实现声明；速率按 Ethernet MAC 服务速率计，不再重复扣 PHY 编码开销。
- 选择有足够内部容量、无其他作业干扰的非阻塞 fabric。四条路径逐包轮询，单向传播偏差为 −1、−1/3、+1/3、+1 us。
  名义 RTT 10 us 是传播和固定处理时间的模型假设，另外显式加入收发序列化及排队。
- 每 rank 1 GiB 的梯度张量可视为大模型梯度/参数块，按 Ring 的 reduce-scatter 和 all-gather 通信依赖执行。
  该选择适用于大块通信；它不代表所有训练框架的默认 bucket 大小。
- 数据、重传、冗余副本各自以 5% 概率被独立擦除；ACK 也独立丢失 5%。这是压力注入条件，不是对健康链路正常丢包水平的描述。

## 有限容量的共享端口

模型使用 Python 3.10 的 `heapq` 事件队列。全部 rank、全部 collective 阶段在同一个时钟下运行。
每张网卡只有一个 400 Gbit/s TX serializer：本 rank 的数据与为上游 rank 生成的 ACK 共同排队。
ACK 在包边界有优先权，不抢占已开始发送的数据包；每一帧，包括丢失的帧，都支付完整发送时间。

每个目的端口还设一个 400 Gbit/s RX serializer，数据与 ACK 共同使用它。
损坏帧在 fabric 内丢弃后不再进入该队列；存活帧在最后一跳再次支付序列化时间。
因此，一个孤立数据包加返回 ACK 的无损确认时间为
`RTT + 2 × (payload + data_overhead + ACK_bytes) × 8 / C`。
这是抽象的存储转发路径，不是具体交换芯片的逐跳模型。

RX 队列容量为每端口 256 KiB，包含正在服务的帧。如果超过容量，整次仿真失败，不把溢出隐藏为“无损”。
内部 fabric 不设超售瓶颈，不模拟拥塞控制、PFC、ECN、故障路径绕行或真实拓扑路由。
只有本组通信的 endpoint fan-in 及路径乱序引起的目的端口队列被显式模拟。
这个配置验证传输恢复能力；引入持续拥塞需要另做实验。

## 固定的候选策略

1. **乱序接收和逐包选择重传。** 发送端收到 CACK、ACK_PSN 和 64 bit SACK 后合并正确认信息。
   SACK 的零位不抹掉已知正确认，也不直接宣判一个包已经丢失。每条连接限制 PSN 跨度。
2. **覆盖式反馈。** 普通 ACK 使用覆盖触发包及前面一段 PSN 的重叠位图。
   新的 64 包区间到来后，为旧区间在 2.5、5 us 后各补发一次反馈；收尾也执行区间反馈。
   ACK 常规合并阈值为 4 包，最长合并等待 0.5 us；重复包、重传包及完成事件及时反馈。
   每个 ACK 在产生时固化快照，排队期间不能读取未来接收状态。
3. **按 RTT 设置恢复定时器。** 早期重传必须同时具有更高 PSN 的正确认和经过乱序保护时间的条件。
   保护时间为 `max(1.1 × RTT, RTT + path_spread + ACK_delay)`，主场景为 12.5 us。
   初始 RTO 为 `1.25 × RTT = 12.5 us`，之后指数退避，最高倍率 8。
   这些是场景适配的固定参数，不是对 UET 规范默认值的声明。
4. **只对尾部恢复添加副本。** 当全部原始包都已发送、剩余待确认包不超过 tail_packets，
   需要重传的包总共最多连续发送 3 个副本。若仍未确认，由下一次定时器继续恢复。
   主场景 tail_packets=32640，但在途 PSN 跨度只有 947；因此这是最后一批在途包的保护，
   并非对整份张量发送三遍。发送端只使用本地状态、ACK 和计时器，不访问随机丢包结果。
5. **给恢复留出窗口空间。** 主场景窗口为 `ceil(8 × C × RTT / (8 × 4224 B)) = 947` 包，
   约 3.699 MiB 的 payload span/连接；每 rank 每阶段一个连接。
   50 us 对照仍使用 8 BDP，自动扩为 4735 包，因此其下降不能简单归因为固定窗口不足。

本实验的物理擦除没有可供转发的残留包头，故 Trim 概率严格为 0；没有假设故障能立即触发 Trim/NACK。
也没有使用编码冗余、无限 ACK 通道、预知丢包或者免计费重传。
设计沿用实验 002 的端点候选，新增实验 004 的共享 NIC 和同步网络模型。
[UE 1.0.3 规范](https://ultraethernet.org/wp-content/uploads/sites/20/2026/08/UE-Specification-1.0.3.pdf)提供乱序可靠传输、SACK 等机制参考；
重叠反馈、补充反馈次数、上述定时器和尾部副本是研究设计。

## AllReduce 依赖及 Goodput

设 rank 数为 N、每 rank 张量大小 S、端口速率 C。
Ring 共 `2(N−1)` 个阶段，每阶段每 rank 向下一个 rank 发送 `S/N` 字节。
一个阶段所有发送端都确认全部数据后才启动下一阶段；时钟、端口队列和旧阶段在途 ACK 都保留。
这个全局步障碍是通信模型的抽象调度器，不另传 barrier 报文，也不模拟 GPU reduction、访存和 host launch 时间。
所测的是 collective 的通信部分，不是 GPU 计算和通信混合的训练吞吐率。
不模拟张量数值运算或真实 NCCL 的细粒度 channel/chunk pipeline。

总时间 T 从第一帧开始到整个操作最终确认，并至少覆盖此时已经预留的所有端口收发序列化时间。
不删除起步和尾部时间，不挑选稳态片段。

```text
每 rank 有效网络字节 = S × 2(N−1)/N
Goodput = 每 rank 有效网络字节 × 8 / (T × C)
bus bandwidth = 每 rank 有效网络字节 × 8 / T
algorithm bandwidth = S × 8 / T
```

有效网络字节只计各逻辑传输的一份必要 payload；重传、副本和 ACK 不增加分子。
对 N=8，网络有效字节为 1.75 S，bus bandwidth 是 algorithm bandwidth 的 1.75 倍。
这是 [NCCL tests 对 AllReduce 的 busbw 换算口径](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)。
本报告带宽单位均为 Gbit/s；NCCL 工具的常见展示单位为 GB/s，不能直接把数字互比。

额外的 permutation 对照是 8 个 rank 同时各向下一个 rank 发送 128 MiB，包含双向数据/ACK 竞争，
计时直到最慢 rank 完成；其 algorithm bandwidth 就等于 bus bandwidth。
它提供不涉及 AllReduce 换算因子的独立验证。

## 可达性的字节预算

忽略尾部、控制包和空闲时，在 IID 5% 擦除下，理想选择重传的数据有效率近似为
`(1−0.05) × 4096/4224 = 92.1212%`。
这是长流的期望参考上界，不是每个有限样本的硬上界。
因此 90% 有约 2.12 个百分点的空间承担反馈和等待，物理上并不矛盾。

每个实测 trial 还严格满足以下字节恒等式：

```text
Goodput = 全部唯一 payload / 全部 TX 字节 × 平均 NIC TX 利用率
全部 TX 字节 = 原始数据 + 重传/副本 + 所有数据开销 + 所有 ACK
```

形式上也可拆成 `payload/(payload+overhead) ÷ 数据发送放大倍数 ÷ (1+ACK/data字节比) × TX利用率`。
由此直接看出重传、控制开销、端口空闲各消耗多少预算，不能靠重新命名指标来达到 90%。
相对无损保留率另列为辅助指标，不用它判定 90% 目标。

## 固定参数、统计及审计

初始试跑只使用 seed 3；其 1 GiB/rank Ring 约为 90.7134%，128 MiB/rank permutation 约为 90.6830%。
正式种子为 11、29、47、71、101、131、173、211、257、307，路径/阶段/rank 使用独立哈希种子空间。
对照取前 5 个正式种子；无损参考确定性运行一次。
验收条件在计算前保存：10 次主实验每一次都 ≥90%，且均值的双侧 95% Student-t 置信区间下界 ≥90%。
正式结果不再参与调参；置信区间只量化独立随机擦除种子的波动，不量化模型误差。

配置、Python 版本、源文件和依赖锁的 SHA-256 在启动时写入 `freeze.json`。
每个任务保存逐连接及逐 NIC 账本；运行结束生成 summary、trials、manifest。
审计重新计算任务覆盖、全部包收齐/确认、时间依赖、字节守恒、每端口收发预算、缓冲上限和均值置信区间。
报告目录额外保存压缩的全部 trial JSON，GitHub 下载者无需再次仿真就能核验汇总。
计时样本中的 `wall_seconds` 是 Python 执行耗时，和模拟出来的通信时间无关。

旧实验 001–003 保持原样；旧结果的精确源码对应 Git 提交 `f59f05c`。
它们将各流反向反馈分别序列化，004 改为真实多端点共享端口，因此应优先使用 004 回答这里的严格带宽预算问题。
新模型的源码摘要只纳入实际依赖的传输文件、运行器及锁文件；报告排版变动不改变仿真摘要。

## 适用范围

本结果适用于所列大消息、短 RTT、IID 擦除、无持续内部拥塞的通信场景。
窗口及 GPU 内存可以支持乱序写入是前提；约 3.699 MiB 是协议窗口的 payload span，并非实测芯片 SRAM 占用。
持续链路故障、相关突发丢包、incast、其他业务竞争、GPU/PCIe 瓶颈和更大规模同步仍须单独验证。
50 us 和小张量对照展示部分边界；本次达到 90% 不改变实验 003 的长距离 AllReduce 结论。
